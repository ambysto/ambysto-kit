# Ambysto Kit 0.3 — wakeups and energy per process (for Power)

Ticket: APS-12 (`ambysto/ambysto-kit#18`, Plane APS-12), part of APS-2. Requested by Ambysto Power (APW-1): its plan group 6, "power by app", is built last and waits for this release.

## Problem

Power estimates which apps use the most power from three inputs per process: CPU time, **idle wakeups** (each one pulls the package out of its low-power state) and the kernel's **billed energy**. It writes no process-reading code of its own (the DevBox rule: process reading lives in the Kit). `AmbystoProcess` already calls `proc_pid_rusage(RUSAGE_INFO_V4)` for every readable process but keeps only the footprint, CPU ticks and disk bytes, and `ProcessSampler` returns **rates only**. Power's plan (after its technical review) needs the **per-interval deltas** and the interval itself, because it sums them over apps and over 5-minute and 1-hour windows; summing rates loses the interval.

Measured on the owner's M1 (Power plan, 2026-10-11): 303 of 309 readable processes have `ri_billed_energy` above 0; idle wakeups range from hundreds to thousands per process. The energy unit is undocumented (it behaves like nanojoules), and whether Intel fills it is unknown.

## Outcome

Kit `0.3`, additive only (a minor release): existing callers build and behave unchanged.

1. **Reader** (`ProcessReader.Usage`): three more counters from the same `rusage_info_v4` call, at no extra system call: idle wakeups (`ri_pkg_idle_wkups`), interrupt wakeups (`ri_interrupt_wkups`), billed energy (`ri_billed_energy`, raw kernel units).
2. **Sampler** (`ProcessSampler` → `ProcessUsage`): besides today's rates, each sampled process carries the **deltas since the previous sample of the same identity**: CPU time in nanoseconds, idle wakeups, interrupt wakeups, billed energy, and the **interval** in nanoseconds; plus idle and interrupt wakeups per second as rates. The same rules as CPU today: keyed by identity (pid + start time), no value on the first sample of an identity, and no value when a counter went down.
3. **Spec** (`docs/spec/process.md`, "A process record" and "Sampling"): the three counters, the deltas and the interval, the rules above, the energy unit stated as undocumented (callers use deltas and shares, never a unit), and Windows notes (no public per-process wakeup counter; energy estimates only through the system resource usage monitor; callers fall back to CPU time).
4. **Spike**: whether `ri_billed_energy` and the wakeup counters are filled on Intel (the owner's MacBook) as on Apple Silicon; the result goes into the spec's macOS note.

### Success criteria (measurable)

| # | Criterion | How it is checked |

## Constraints

- Swift 6, macOS 14+, public APIs only (`proc_pid_rusage`, public `sys/resource.h` fields), no new dependencies, no extra system call per process.
- **Rating** (Kit CLAUDE.md): new reader fields and additive API are MEDIUM (builder, then reviewer); the delta and "counter went down" rules are sampling rules, which are HARD, so the main session writes them into the spec and the reviewer checks the code against it.
- **Release line** (Kit decision 2026-10-12): this merges to `main` as usual, then is cherry-picked onto `release/0.2` in its own reviewed PR and tagged `v0.3.0` there (after `v0.2.0`). It must therefore touch only `AmbystoProcess`, its tests, `docs/spec/process.md` and the probe, never the suite bar files, so the pick applies cleanly; CLAUDE.md's test counts are edited separately on each line.
- Power moves its Kit pin to the 0.3 merge commit for its group 6, then to `from: "0.3.0"` before it ships.
- Everything on GitHub in English; feature branch and PR; tickets synced on GitHub and Plane.

## Out of scope

- Grouping processes into apps and the power estimate itself (Power's `PowerImpact`, Power's spec).
- GPU energy, per-thread data, `ri_serviced_energy` (not requested).
- Windows code.

## Decisions (owner, 2026-10-12)
1. **Billed energy is reported raw:** the counter and its delta, 0 stays 0. The Kit does not decide "no energy anywhere"; Power applies its own rule (energy non-zero for at least one process in the window, else the CPU-time fallback). This replaces the ticket's "`nil` when the kernel reports 0 everywhere".
2. **One counter went down → nothing for that process in that sample:** no deltas and no rates, as CPU and disk behave today (its counters are not comparable after a reused identity or a reset).

# Ambysto Kit 0.1.0 — offline license keys

Tickets: APS-10 (this work), part of APS-2 (Ambysto Kit). Supersedes the format sketch in AO-5 (`ambysto/ambysto-optimer#2`). Unblocks Proof 12 of Ambysto Space v1 (ASP-2).

## Problem

Every Ambysto app needs the same answer to one question: "does this person have Pro for this app?" Today nothing answers it.

- **Space v1 is built but cannot honour a key.** Its license seam refuses every key with "License activation arrives in an update", so Proof 12 (a key whose `products` contains `space` unlocks Pro offline) is blocked.
- **The launch plan needs keys now.** The owner decided (2026-10-10) not to charge at first and to gift Pro keys to early users. A gift is still a key: it has to be issued, verified and revocable.
- **The format must be shared.** The suite strategy (APS-1, decision 7) puts cross-app contracts in the Kit spec, versioned with the Kit. One bundle key must unlock every app it lists, and the Windows apps must verify the same keys from the spec without reading Swift.
- AO-5 settled the approach (signed, offline, `products` list, no phone-home) but was written for Optimer alone (`AOPRO-` keys, `.optimerkey` files, Ed25519) and never built.

**What a license is for (owner, 2026-10-10).** It is an honesty-based deterrent, the WinRAR model: "Registered to <name>" in About, a revocation list, nothing more. Cracking desktop software is easy, especially with AI tools; Space and the other apps do not try to stop it. The goal is a clean, cheap, correct mechanism, not protection.

## Outcome

Kit `0.1.0`: the first tagged release of `ambysto/ambysto-kit`, containing **only the license module**. Apps depend on it with SwiftPM `from: "0.1.0"`.

> Owner decision 2026-10-11: Kit 0.2 (process reading and the safety core) was merged before the production key existed, so the first tag is **`v0.2.0`** and carries the license module too; apps depend on `from: "0.2.0"`. Earlier `v0.1.0` wording is kept as written.

### 1. A platform-neutral license spec — `docs/spec/license.md`

- Payload fields: `licensee` (a name; shown as "Registered to …"), `products` (from a fixed product registry: `optimer`, `steady`, `space`, `devbox`, `power`, `tune`, `guard`; new ids are added only by a Kit version bump), `issuedAt`, `updatesUntil` (optional; absent = updates for life), `seats` (informational), `keyID`, and a format version.
- Canonical binary encoding, an **ECDSA P-256 signature** over it (64 bytes, raw `r‖s`, SHA-256), and the text form: **`AMB-` followed by Base32 in groups of five** (for example `AMB-K7Q2M-…`). Pasting is the normal path; the form survives email and chat (no ambiguous characters, case-insensitive, dashes and spaces ignored). P-256 is built into both CryptoKit and .NET, so neither platform needs a third-party library (owner decision, 2026-10-10; replaces Ed25519 from AO-5).
- **One key system for every platform** (owner decision, 2026-10-10): the same key unlocks an app on Mac and on Windows; `seats` counts machines across both. Keys are issued in one place (the owner's Mac); apps on every platform only verify, with the public key built in.
- The **`.ambystokey` file**: the same key in a small file; double-clicking it opens the app that can use it.
- Signing-key rotation: each key names the signing key that made it, and a release can trust more than one public key.
- Revocation: a list of revoked `keyID`s compiled into each Kit release.
- **Test vectors**: valid keys (single app, suite, with and without `updatesUntil`), tampered payload, wrong signature, unknown signing key, revoked key, malformed text. They are generated once with a throwaway test signing key whose private half is published in the spec on purpose, and is never trusted by release builds.

### 2. Swift package — `AmbystoKit`, library `AmbystoLicense`

- `verify(_ text: String) -> LicenseResult` (valid license or a plain-language reason) and `License.covers(product:)`, `License.allowsUpdates(builtOn:)`.
- Reads a pasted key or an `.ambystokey` file.
- Fully offline: no network call, no device identifier, nothing sent anywhere.
- Public Apple API only (CryptoKit `P256.Signing`). No third-party dependency.

### 3. Issuing tools (owner's Mac only) — `scripts/`

- `new-signing-key`: creates the production P-256 signing key pair. The private half goes **straight into the macOS login Keychain** and is never printed, logged or left on disk. The Keychain item **trusts no application**, so macOS asks for the login password every time anything reads it: a coding agent running as the same user cannot read it silently; the public half is printed for the Kit source. It also writes one **offline backup**: an AES-256 encrypted disk image (built-in `hdiutil`) holding the private key, for the owner to keep on a USB drive stored apart from the Mac (owner decision, 2026-10-10: Keychain instead of 1Password; no new tool, no subscription).
- `issue-license`: reads the private key from the Keychain at run time (macOS may ask for the login password), prints one key and writes one `.ambystokey` file. Inputs: licensee, products, seats, optional `updatesUntil`. Every issued key is appended to a local ledger (keyID, licensee, products, date) kept outside the repo, so a key can be revoked later.
- `import-signing-key`: loads the private key from the encrypted backup into the Keychain of another Mac (a machine upgrade), with the same "ask every time" rule.
- **Where the key lives (owner context, 2026-10-10):** the owner is moving to a Mac Studio that runs coding agents continuously. The production key is created (or imported) on the Mac used to issue keys, and coding agents on that Mac run under a separate standard macOS user, never under the owner's user, so they cannot reach the owner's Keychain, files or tokens at all. Nothing needs the production key until keys are issued; development and tests use the published test key.
- If the Mac and the backup are both lost, keys already issued keep working; a new signing key is created and trusted in the next Kit release (rotation, §1).
- The scripts read and write the private key through one small storage step, so moving it to a password-manager vault later (for example Bitwarden, if keys must be issued from several machines) changes that step only, not the key format or any app (owner, 2026-10-10: Keychain first for low cost; change when needed).

### 4. Launch-phase gift keys (owner decision, 2026-10-10)

- Gifted keys are **for life**: no `updatesUntil`; `seats: 3`, informational only, never enforced offline.
- `products` is one app (for example `["space"]`) or the whole suite.
- Keys are gifted **unconditionally**. Trustpilot's guidelines forbid incentives for reviews, so a key is never tied to writing one.

### 5. Space adopts it

Ambysto Space replaces its pending verifier with the Kit's (one line) and drops nothing else. Space's Proof 12 runs with keys from `issue-license`.

## Constraints

- Swift 6, macOS 14+, SwiftPM library; CryptoKit only; no third-party dependencies.
- Offline only: no network, no telemetry, no device fingerprint.
- Secrets follow `bto-secrets`: the private key lives only in the owner's Keychain and the encrypted offline backup; no secret in the repo, CI, logs or chat. The owner runs `new-signing-key`; the agent never sees the private key.
- Keep it simple: no obfuscation, anti-tamper, jailbreak/crack detection or online checks (see "What a license is for").
- The spec names behaviour and bytes, never Swift types, so the Windows (.NET) verifier can be written from it alone.
- Semver: format changes that break old keys need a major version; adding a product id or a revoked keyID is a minor or patch release.
- Everything on GitHub is in English; feature branch and PR, never a direct push to `main`; commits end with the Co-Authored-By line; tickets kept in sync on GitHub and Plane.

## Out of scope

- The rest of APS-2: safety core, brand tokens, floating mini bar, suite discovery, merged mini bar (Kit 0.2 and later).
- Optimer adopting the Kit license (AO-5 follow-up after this release), and Steady (no Pro tier yet).
- Online activation, seat enforcement, a revocation server, device binding.
- Any anti-cracking measure: obfuscation, integrity checks of the app, hidden checks, server validation.
- Separate keys or formats per platform.
- Payment and a sales page (APS-5), prices (APS-3), refund terms (APS-4).
- The Windows (.NET) verifier; only its spec and test vectors are in scope.
- Key transfer and self-serve lost-key recovery (support handles them manually from the ledger).
